# 観測された結果

実験から出た事実と、それが企画に対して持つ意味。**都合の悪い結果ほど先に書く。**

観察したいのは、判断を挟むことがコスト・所要時間・リトライ・手戻り・人間の介入にどう効くか。
「Jev を使えば効率化する」という前提は置かない。

## F-003: 判定は揺れなかった。LLM も Jev も

各 probe を 10 回ずつ、両方の判定者に投げた。

| probe | 問い | LLM | Jev |
| --- | --- | --- | --- |
| 001 | エラーコードは実際に起きたことと一致しているか | no 10/10 | no 10/10 |
| 002 | この変更に人間のレビューが必要か | yes 10/10 | yes 10/10 |
| 003 | （対照）コメント修正だけの変更にレビューが必要か | no 10/10 | no 10/10 |

**判定は 3 本とも一致した。** Jev が LLM より正しく判断した、という結果は出ていない。
「LLM は揺れるから使えない」という主張は、少なくともこの範囲では成立しない。

LLM の理由の文章は毎回違ったが、構造化出力で受ければ判定には影響しない。

## F-004: 差が出たのは速度と、返る形

同じ probe、同じ state / instructions / criteria。

| probe | LLM 所要 | Jev 所要 | LLM 1判定 | Jev 1判定 | 倍率（時間 / 費用） |
| --- | --- | --- | --- | --- | --- |
| 001 | 4,955ms | 267ms | $0.0192 | $0.0000291 | 19x / 661x |
| 002 | 7,995ms | 256ms | $0.0221 | $0.0000752 | 31x / 293x |
| 003 | 2,973ms | 290ms | $0.0173 | $0.0000251 | 10x / 689x |

Jev の確率は 001 が 0.115、002 が 0.745、003 が 0.089。

Jev の確率のばらつきは 10 回で ±0.01。

**二値では潰れていた差が、確率には出ている。**
002 は 0.745、003 は 0.089。LLM はどちらも「yes」「no」としか返さないので、
「レビューが要るが確実ではない」と「明らかに要らない」の区別が残らない。
閾値を置いて振り分けるには、この差が要る。

ただし 002 の 0.745 が妥当な値かどうかは、まだ検証していない。
正解ラベルの付いた事例を集めないと、較正が正しいかは言えない。

価格は [docs.typesafe.ai/models](https://docs.typesafe.ai/models) に載っている。
Jev 1.13 は入力 $0.042 / Mtok、**出力トークンは無料**。
生成モデルと逆の形で、長文を書かせない用途ほど有利になる。

同じ `state` に対する質問は並列に評価され、入力トークンを共有する。
独立した問いをまとめて 1 リクエストに詰めれば、10 問でも 1 問と費用がほぼ変わらない。
ハーネスの判断点を 1 箇所にまとめる設計が、そのまま費用に効く。

レート上限は 250,000 tok/s・1,200 req/min。文脈長は 1 リクエスト 64k、
`state` と最長の質問で 32k。上限は予告なく変わるとドキュメントに明記されている。

追記（2026-11-02、`docs/detailed-results.md` から移した）: 実装自体には 1 タスク $0.2〜0.3 かかった。
仮に判定を LLM と同程度の 1 回約 $0.02 としても、実装費用に比べた割合は約 1 割。判定 1 回の費用差が、そのまま開発全体の節約になるわけではない。

## 参考: 計算的センサーとの比較

`npm run check`（型チェック 0.8 秒 + lint 1.2 秒 + テスト 1.6 秒）は一式 3.7 秒、追加コストなし。

Jev の 1 判定 267ms は、計算的センサーと同じ桁に乗っている。
LLM の 5〜8 秒は、変更のたびに回すには重い。

## F-005: 質問文を日本語にしても、判定は変わらなかった

ドキュメントには「英語が主要な訓練言語で、CJK を含む他言語は同等ではない」とある。
`state` を 1 バイトも変えず、`instructions` と `criteria` だけ英語にして測り直した。

| probe | 日本語 | 英語 | 差 |
| --- | --- | --- | --- |
| 001 | 0.115 | 0.100 | -0.015 |
| 002 | 0.745 | 0.785 | +0.040 |
| 003 | 0.089 | 0.084 | -0.005 |

判定（0.5 を閾値とした yes / no）は 6 本すべて一致した。所要時間も差が無い。

ただし**答えが割れる問いでだけ差が大きい**。
極端な 001 と 003 は 0.015 以内、曖昧な 002 だけ 0.04 動いた。

実務上の意味はこう。閾値を 0.5 付近に置くなら日本語で問題ない。
0.75 付近のような際どい位置に置くなら、質問文の言語で振り分け先が変わりうる。

## F-030: 大量の振り分けでは、Jev は Haiku 5.5 より安いとは限らなかった。日本語では正解率も低かった

出典: `experiments/classify/results-*.jsonl`、`scripts/classify-judge.ts`、`scripts/classify-baseline.py`、`npx tsx scripts/classify-report.ts`。

費用のほぼ全部が判定になる場面として、問い合わせの振り分けを測った（2026-10-13）。

### データ

どちらも人が正解を付けた公開データで、CC BY 4.0。`experiments/classify/data/` に LICENSE ごと置いた。

- Banking77（PolyAI）: 銀行への問い合わせ。英語、77 種類。test 3,080 件、train 10,003 件
- MASSIVE ja-JP（Amazon）: 音声アシスタントへの話しかけ。人が英語から訳した日本語、60 種類。test 2,974 件、train 11,514 件

人が付けた正解つきで商用利用できる、日本語の問い合わせのデータは見つからなかった。

### 方式

- Jev: 種類の名前を並べた Choice 1 問。1 件 1 リクエスト、並列 8。test 全件
- Haiku、Sonnet: `claude -p` に同じ種類の名前を渡し、JSON スキーマの enum で 1 つ選ばせる。並列 3。test から等間隔に抜いた 400 件
- 古典的な分類器: TF-IDF とロジスティック回帰を train で学習する。英語は単語、日本語は文字の n グラム

Jev と LLM には種類の名前だけを渡し、説明や例は付けていない。学習データも使わない。

### 結果（LLM と同じ 400 件）

| 方式 | Banking77 | MASSIVE ja |
| --- | --- | --- |
| Jev | 81.0% | 79.5% |
| Haiku | 83.2%（399 件、失敗 1） | 83.8% |
| Sonnet | 82.8% | 84.8% |
| 古典的な分類器（train 全件で学習） | 90.0% | 82.0% |

test 全件では、Jev が 80.4% と 80.9%、古典的な分類器が 89.4% と 83.8%。

### 差は偶然か

同じ 400 件で、片方だけが正解した件数を数え、McNemar の正確検定に掛けた。

| 比べた組 | Jev だけ正解 / LLM だけ正解 | p 値 |
| --- | --- | --- |
| Banking77、Jev と Haiku | 11 / 20 | 0.15 |
| Banking77、Jev と Sonnet | 18 / 25 | 0.36 |
| MASSIVE ja、Jev と Haiku | 10 / 27 | 0.008 |
| MASSIVE ja、Jev と Sonnet | 5 / 26 | 0.0001 未満 |

英語の Banking77 では、差は偶然と区別できない。日本語の MASSIVE では、LLM のほうが正しい。

LLM は `claude -p` の既定のまま、考える段（thinking）が入っている。1 件で 200 トークンほど考えていた。
API で考える段を切って呼ぶと、正解率が下がる可能性がある。測っていない。

### 費用：`claude -p` の値は使えない

`claude -p` は、1 回ごとに Claude Code の前置きを約 2.5〜2.8 万トークン送っていた。問い合わせと種類の一覧はその 3% ほど。
記録の費用（1,000 件 Haiku $2.1、Sonnet $38）はほぼ前置きの費用で、API を直接呼んだときの費用ではない。
1 件の待ち（約 5 秒）も、Claude Code の起動と考える段を含む。

そこで、前置きを差し引いた入力トークンを測り、公式の単価（2026-10-13 に料金表で確認）から API の費用を計算した。
前置きは、最小の入力（system "x"、種類 1 つ、本文 "x"）との差で除いた。料金表の単価で `claude -p` の記録の費用を計算し直すと一致した。

- 入力: Banking77 は約 860 トークン、MASSIVE ja は約 520 トークン。構造化出力の道具の前置き 406 トークンを足して見積もる
- 出力: 種類の名前の JSON で約 20 トークン。考える段なし
- 単価（100 万トークン）: Haiku 5.5 は入力 $0.10、キャッシュ読み $0.01、出力 $0.50。Sonnet 5.5 は入力 $2、キャッシュ読み $0.10、出力 $10。Jev は入力 $0.042、出力は無料
- 種類の一覧は毎回同じなので、プロンプトキャッシュに乗る（最小 512 トークン）

| 方式 | 1,000 件あたり（Banking77） | 同（MASSIVE ja） |
| --- | --- | --- |
| Jev（実測） | $0.044 | $0.035 |
| Haiku 5.5、キャッシュなし（計算） | $0.14 | $0.10 |
| Haiku 5.5、一覧をキャッシュ（計算） | $0.025 | $0.021 |
| Sonnet 5.5、キャッシュなし（計算） | $2.7 | $2.1 |
| Sonnet 5.5、一覧をキャッシュ（計算） | $0.37 | $0.33 |

**Haiku 5.5 で一覧をキャッシュすれば、Jev より安くなる。**（下の訂正で、出力を少なく見積もった誤りと分かった。考える段を外しても Jev とほぼ同じ）Haiku 5.5 の入力単価は Jev の 2.4 倍しかなく、キャッシュ読みは Jev の 4 分の 1 になるため。
Batch API を使えば、さらに半額になる。

待ち時間は、API を直接呼べないので測れていない。Jev の実測は 1 件 0.18 秒（中央値）。

### 訂正（2026-10-14）: 出力を 20 トークンと置いたのは少なすぎた。考える段込みの費用も足した

上の費用は、出力を約 20 トークン（種類の名前の JSON）と置いて計算した。トークン数を記録する版で Haiku を各 100 件流し直すと
（`classify-judge.ts <データ> tokens:haiku -- --sample 100`、計算は `scripts/classify-cost.py`）、出力は平均 287 と 254 トークンで、
うち考える段が 227 と 194、残りの構造化出力の呼び出しが約 60 トークンだった。前置きは件ごとに数百トークン揺れるので、
毎回変わる問い合わせの文を 0〜100 トークンの幅で置いた。

| 方式（1,000 件あたり） | Banking77 | MASSIVE ja |
| --- | --- | --- |
| Jev（実測） | $0.044 | $0.035 |
| Haiku、一覧をキャッシュ、考える段なし | $0.042〜0.051 | $0.041〜0.050 |
| Haiku、一覧をキャッシュ、考える段込み | $0.156〜0.165 | $0.139〜0.148 |
| Haiku、キャッシュなし、考える段なし / 込み | $0.153 / $0.267 | $0.146 / $0.243 |

**「Haiku 5.5 で一覧をキャッシュすれば Jev より安い」は誤り。** 考える段を外してキャッシュしても、Jev とほぼ同じ。
正解率を測った条件（考える段込み）では、キャッシュしても Jev の 3.5〜4 倍。考える段を外した Haiku の正解率は測っていない。
API で構造化出力を使う方法によっては出力が 60 トークンより短くなる可能性があり、その場合は Haiku が少し安くなる。
Sonnet の出力トークンは記録していないので、Sonnet の費用は上の表のまま（出力 20 トークンの置き方）で、低めに出ている可能性がある。
この 100 件の API の時間は、中央値 1.9 秒と 1.8 秒。


確信度が線以上のものだけ自動で振り分け、残りを人か LLM に回す使い方。

| 線 | 自動で振り分けた割合 / その正解率（Banking77） | 同（MASSIVE ja） |
| --- | --- | --- |
| 0.7 | 84.7% / 87.6% | 82.3% / 89.3% |
| 0.9 | 69.7% / 92.5% | 68.4% / 93.7% |

正解が Jev の上位 3 つに入った割合は 91.4% と 93.5%。

### 正解付きのデータが何件あれば、古典的な分類器が Jev を上回るか

train から乱数の種を固定して 3 通り抜いて学習し、test 全件で測った平均。

| 学習の件数 | Banking77 | MASSIVE ja |
| --- | --- | --- |
| 100 | 19.5% | 29.4% |
| 300 | 39.9% | 49.4% |
| 1,000 | 65.8% | 67.7% |
| 3,000 | 82.0% | 77.7% |
| 全件 | 89.4% | 83.8% |

Jev（80% 前後）を上回るのは、Banking77 で 3,000 件前後、MASSIVE ja で 3,000 件と 1 万件の間。

埋め込みの分類器（`scripts/classify-embed.py`、multilingual-e5-small を手元の Mac で計算、同じ種で抜く）:

| 学習の件数 | Banking77 | MASSIVE ja |
| --- | --- | --- |
| 100 | 18.9% | 29.0% |
| 300 | 45.0% | 51.2% |
| 1,000 | 75.2% | 70.6% |
| 3,000 | 86.5% | 79.2% |
| 全件 | 90.9% | 83.5% |

TF-IDF より伸びは早いが、Jev を上回るには Banking77 で 1,000〜3,000 件、MASSIVE ja で 3,000 件以上が要る。
件数は種類を問わず無作為に抜いたので、100 件では 1 件も無い種類が出る。種類ごとに数件ずつ集めれば、もっと少ない件数で伸びる可能性がある。

### ここまでで言えること

- 正解率は、英語では Jev と LLM の差が偶然と区別できない。日本語では LLM のほうが 4〜5 ポイント正しい
- 費用は、Haiku 5.5 でキャッシュを使い考える段を外せば Jev とほぼ同じ。考える段込みでは Jev の 3.5〜4 倍（訂正後の値）
- 正解付きのデータが数千件あるなら、手元で動く分類器のほうが正確で、判定の費用もかからない
- Jev に残る利点は、確信度が付くこと、速さ（ただし API の LLM とは比べていない）、プロンプトを組まずに済むこと

制約: API の LLM の費用は計算で、実測ではない。待ち時間は比べていない。
LLM は 400 件だけ。どの方式も、種類の説明や例を渡したときの伸びは測っていない。

### 追記（2026-11-02）: TF-IDF 分類器の C を決めた経緯

TF-IDF 分類器のロジスティック回帰は、正則化の強さを C=10 にしている。この値を決めた経緯は記録に残っていない。
そこで 2026-11-02 に、学習用データだけの 5 分割交差検証で C を比べた。

| C | 交差検証、英語 / 日本語 | 評価 400 件、英語 / 日本語 |
| --- | --- | --- |
| 1 | 84.6% / 78.5% | 85.8% / 79.5% |
| 10 | 88.0% / 83.1% | 90.0% / 82.0% |
| 100 | 88.2% / 83.3% | 90.3% / 81.3% |

交差検証では C=10 と 100 の差が 0.3 ポイント未満だった。評価用データでも、C を 100 にして本文の結論は変わらない。

## F-031: レシピ 2「1 つの文に質問をたくさん投げる」。線を自分のデータで決めれば、Haiku と並んだ

出典: `experiments/recipes/goemotions/`、`scripts/recipe-multilabel.ts`、`python3 scripts/recipe-report.py`（2026-10-14）。

データは GoEmotions（Google、Apache 2.0）。Reddit のコメントに、人が 28 種類の感情（neutral を含む）を付けた。1 件に複数付くことがある。
test 5,427 件、線を決めるための dev 5,426 件。

Jev は感情ごとに Noul を 1 問、28 問を 1 リクエストで投げた。LLM は `claude -p` で、当てはまる感情を配列で返させた（test から等間隔に 300 件）。
LLM の費用の出し方は F-030 と同じで、前置き（Haiku 26,071、Sonnet 26,073 トークン）を差し引いて公式の単価で計算した。

### 問いの数を増やしたときの Jev

同じ 50 件で、問いの数だけを変えた（`results-scaling.jsonl`）。

| 問いの数 | 入力トークン（中央値） | 待ち（中央値） |
| --- | --- | --- |
| 1 | 292 | 152 ms |
| 7 | 376 | 157 ms |
| 14 | 477 | 152 ms |
| 28 | 682 | 156 ms |

28 問を 1 リクエストにまとめると、入力は 1 問の 2.3 倍で、待ちは変わらない。1 問ずつ 28 回送ると、入力は 28 倍になる。

### 正解率

| 方式 | micro F1（300 件） | 完全一致（300 件） |
| --- | --- | --- |
| Jev、線 0.5 | 0.250 | 2.3% |
| Jev、感情ごとの線を dev で決めた | 0.375 | 13.0% |
| Jev、全体で 1 本の線を dev で決めた（0.9） | 0.334 | 22.7% |
| Haiku | 0.341 | 12.7% |
| Sonnet | 0.404 | 19.0% |

線 0.5 では、Jev は 1 件に平均 4.8 個の感情を付けた（正解は平均 1.2 個）。Noul の値はそのまま 0.5 で切れる確率ではなかった。
線は dev だけで決め、test では決めていない。線より上が 1 つも無いときは、一番高いものを 1 つ選ぶ（正解は必ず 1 つ以上ある）。

感情ごとの線の Jev は、完全一致で Haiku と差が無い（Jev だけ正解 25、Haiku だけ正解 24、p=1.0）。Sonnet には負ける（16 対 34、p=0.015）。
全体で 1 本の線（0.9）の Jev は、完全一致では Haiku に勝ち（47 対 17、p<0.001）、Sonnet と差が無い（37 対 26、p=0.21）。
F1 と完全一致のどちらを取るかで、線の決め方が変わる。

### 費用と待ち

| 方式 | 1,000 件あたり | 待ち（中央値） |
| --- | --- | --- |
| Jev（実測） | $0.029 | 163 ms |
| Haiku（API 換算、考える段なし / 込み） | $0.21 / $0.39 | 測れていない |
| Sonnet（同） | $2.36 / $2.85 | 測れていない |

LLM は答えの感情の数だけ出力が増え、出力の単価は入力の 5 倍。Jev は出力が無料なので、問いを増やしても入力の分しか増えない。
`claude -p` では考える段を切れなかった（`--effort low` や `alwaysThinkingEnabled: false` でも Haiku は 200 トークン以上考えた）。
LLM の正解率は考える段込みの値で、考える段なしの正解率は測れていない。

### 訂正（2026-10-15）: 28 回送り直すことと、入力トークンが28倍になることは別

F-031 の「1 問ずつ28回送ると、入力は28倍になる」は、state を送り直す回数と、リクエスト全体のトークン数を混同した表現だった。
問いの文の長さも入力トークン数に影響する。個別の28問を送ったときの総トークン数は、この測定では確認していない。
正確に言えるのは「同じstateを28回送り直し、入力の共有による節約ができなくなる」。まとめた28問の入力が1問の2.3倍という実測結果は変わらない。

## F-032: レシピ 3「毎回違う長い文を読ませる」。Jev は Haiku の 4〜10 分の 1 の費用で、正解率は 6 ポイント低い

出典: `experiments/recipes/contractnli/`、`scripts/recipe-contract.ts`、`python3 scripts/recipe-report.py`（2026-10-14）。

データは ContractNLI（Hitachi America、CC BY 4.0）。秘密保持契約 123 通（test）それぞれに、決まった 17 個の条項について
「書いてある」「反対が書いてある」「触れていない」を人が付けた。契約書は 1,231〜41,779 字、中央値 9,614 字。

Jev は 1 通に 17 問の Choice を 1 リクエストで投げた。LLM は 17 条項を system に並べ、契約書を本文で渡し、17 個の答えを返させた。
LLM も 123 通すべてを回した。

| 方式 | 正解率（2,091 判定） | 1,000 通あたり |
| --- | --- | --- |
