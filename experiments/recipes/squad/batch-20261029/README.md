# 実験4：段落ごとの判定をまとめて送る

本の掲載コードに対応する再計測です。
SQuAD 2.0の同じ300問・同じ段落を、Jev 1.13.0とPython SDK 0.6.0で測りました。
モデル・データのハッシュ・質問ID・リクエストのハッシュは`manifest.json`にあります。
段落の選択は、確率が最大の段落を選ぶ方法です。同点なら元の順で先の段落を選びます。

| 方式 | 正解数 / 300問 | リクエスト数 |
| --- | --- | --- |
| separate：段落ごとに別送信 | 276（92.0%） | 11,048 |
| batch：全段落を共通state、各Noulから配列位置で参照 | 159（53.0%） | 300 |
| batch-local：質問を共通state、段落を各Noulへ直接渡す | 279（93.0%） | 300 |

本のコードは`batch-local`です。
`batch`は、`paragraphs[i]`を判定するよう英語のinstructionsに書いています。
質問IDだけでは対象の段落を指定できないためです。
この指示形式が有効に働いたとは言えません。
この結果を、全段落を共有するあらゆる入力形式の成績とは扱いません。

| 方式 | 1問の概算費用 | 1問の待ち時間の中央値 |
| --- | --- | --- |
| separate | $0.00080264 | 0.504秒 |
| batch | $0.00039648 | 0.213秒 |
| batch-local | $0.00039343 | 0.206秒 |

費用はAPI応答の入力トークン数に、100万トークンあたり$0.042を掛けました。
入力トークン数は、それぞれ平均19,110.45、9,440.07、9,367.41です。
3方式の全900件は成功しました。記録した総費用の概算は$0.47776596です。
待ち時間は300問すべてで、送信開始から全判定の受信までを測りました。
別送信は同時16リクエストまで、まとめる2方式は1問につき1リクエストです。
方式の実行順は質問ごとに正順・逆順を交互に切り替えました。
SDKの初期化・データ読込・段落のソートは待ち時間に含めません。
単一環境での1回の測定であり、別の時刻や回線での速度を保証する値ではありません。

## 既存の比較との関係

元の`results-jev.jsonl`などは変更していません。
旧300問のJevは279問正解でした。同じ入力の今回の別送信は276問です。
再実行時にスコアや順位が変わる例もあり、今回の3問差で精度の向上を主張しません。
一括送信の入力形式を2種類試したことも含め、評価用データでの比較です。
別データでの最終確認は行っていません。

Haikuは保存済みの100問の結果を再利用しました。HaikuのAPIは再実行していません。
同じ100問では、batch-localとHaikuがともに92問正解でした。
片方だけが当てた件数は、それぞれ4問です。
旧Jevの90%を、新しいコードの結果として使っていません。
BM25の77%は、同じ300問に対する既存の手元の計算です。
記事の段落を選ぶ評価であり、その資料から作った最終回答は採点していません。

## 再実行するときの規則

`--budget-usd`は、記録済みの利用量が上限へ達したら次の呼び出しを止める指定です。
実行中の呼び出しは上限を超える可能性があります。請求額を厳密に制限するものではありません。

`--methods batch-local`を付けると、本の方式だけを測れます。
`--limit 5`を付けると、最初の5問だけで動作を確かめられます。
同じ出力先・同じ引数で再実行すれば、成功済みの質問は呼び直しません。
入力・モデル・方式などが違う記録への追記は拒否します。
API応答を受け取れなかった呼び出しの課金は不明として残します。
エラー後に再開する場合は、保存記録と利用量を先に確認します。

## ファイル

- `manifest.json`：測定条件、対象ID、入力のハッシュ
- `results.jsonl`：質問ごとの確率・利用量・待ち時間・モデル名
- `report.json`：保存結果から作った集計

再集計と再実行のコマンドは、[再実行手順](../../../../docs/reproduction.md#rerank-batch)にあります。
